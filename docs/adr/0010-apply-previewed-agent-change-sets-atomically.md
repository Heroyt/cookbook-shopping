# ADR 0010 — Apply previewed Agent Change Sets atomically

AI agents mutate Family-owned Cookbook and Meal Planning data by first validating and previewing an immutable Agent Change Set, then explicitly applying that exact revision in a second API request. Application is atomic and may include creates, updates, archives, restorations, and deletions, but never Family Access or Agent Credential operations. An unordered list of typed operations references existing records by stable API identifiers and new records by request-local references; the server resolves dependencies and rejects name conflicts instead of guessing matches.

The API invokes the same application actions and invariants as the web interface: `destructive:write` permits only domain-approved deletion and never force-deletes archive-only Recipes or Ingredients. Preview returns blocking errors, effects, and stable warning codes; apply requires the preview digest and acknowledgement of every warning.

Applying a preview fails if relevant Family data changed after validation, requiring a fresh preview. A required client request identifier makes identical retries idempotent and conflicts when reused with a different payload. Unapplied previews expire after 24 hours, while applied Change Sets become immutable Family-owned history containing server-recorded credential, issuer, timestamps, digest, outcome, and optional caller-supplied title, source URLs, and note; an AI agent cannot delete that history. This retains agent autonomy, provenance, and full domain lifecycle coverage while reducing accidental, stale, or payload-swapping changes; it adds a two-step protocol, retained history, and explicit retry behavior.

Existing records use their integer database identifiers plus `updated_at` as the optimistic-concurrency value. Update operations distinguish assigned values from cleared fields through `set` values and an `unset` list. Preview and apply execute synchronously with configurable initial limits of 250 operations and 2 MiB of JSON per Change Set; photos and other new media are outside the initial Agent API.

Updates replace a complete nested collection when it is supplied, including Recipe Ingredients, Recipe Steps, Recipe Tags, Ingredient package quantities and alternatives, or a Store's ordered Sections; omitted collections remain unchanged. The Agent Catalog exposes both active and archived records with explicit status and filters. Errors use stable machine-readable codes with English messages, JSON paths, operation references, and structured details.

Per-credential rate limits initially allow 120 catalog reads, 20 previews, and 10 apply attempts per minute and return standard retry guidance. Applied history retains the full canonical request, previewed effects and warnings, acknowledgements, local-reference mappings, final result, credential, issuer, timestamps, payload digest, outcome, and optional caller provenance until a Family member deletes it through the web interface.

Any Agent Credential may list and inspect all Agent Change Set History in its Family through `content:read`, but no agent may delete history. Only the exact credential that created a preview may apply it. The v1 Agent API exposes catalog discovery and lifecycle operations for Stores, Store Sections, Ingredients, Recipe Tags, Recipes, and Calendar Entries. Package quantities, nutrition, alternatives, Store Section order, Recipe Ingredients, Recipe Steps, and Recipe Tags remain nested collections. Family Access, Simple Plans, Shopping Generation, Saved Shopping Lists, and media are outside v1.

The JSON contract uses canonical English domain terms, `snake_case` field names, and lowercase action and status values. Exact decimals, including quantities and Serving Counts, are encoded as strings. Meal Labels use the canonical Czech string values defined in the glossary. Technical timestamps use RFC 3339 UTC, Calendar dates use `YYYY-MM-DD`, and Recipe preparation and cooking durations use integer minutes.

Every operation carries a unique caller-defined `operation_id`; create operations additionally declare a unique `local_ref` for cross-references within the unordered Change Set.

The v1 HTTP interface is intentionally compact: `GET /api/v1/catalog` returns the complete compact Family catalog with optional resource-type filters, `GET /api/v1/catalog/{resource_type}/{id}` returns aggregate detail, `POST /api/v1/change-sets` validates and creates a preview, `GET /api/v1/change-sets` and `GET /api/v1/change-sets/{id}` expose previews and history, and `POST /api/v1/change-sets/{id}/apply` applies a preview. There are no separate mutation endpoints.

A persisted Change Set starts as `previewed` and may become `applied`, `expired`, `invalidated`, or `stale`. Retryable server failures leave it previewed, while invalid input is never persisted. Once the 24-hour window ends, the API treats the preview as expired and the scheduler permanently removes the unapplied record.

Update `set` values cannot be `null`; `unset` clears nullable scalars or singular relationships. Omitted fields and collections remain unchanged. A supplied empty collection intentionally clears that whole collection when its aggregate invariants permit.

Users inspect applied records on a Current Family Agent Change History page that can filter by credential, issuer, date, resource type, and outcome. Any Family member may delete history through a consequence-stating confirmation dialog; deletion never rolls back domain changes.

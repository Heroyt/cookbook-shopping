# Data structure

## Implemented persistence

The repository persists Users, authentication infrastructure, Families, roleless Family Memberships, each User's nullable Current Family preference, Stores, reusable Store Sections and their ordered associations, concrete packaged Ingredients, direct Alternative edges, Ingredient Nutrition Profiles, complete Recipe aggregates, Recipe Tags and assignments, Calendar Entries, and immutable Saved Shopping Lists. Media uses the configured private filesystem rather than database blobs. Simple Plans, Calendar Days, Calendar Selections, generated Shopping Lists, and Alternative session choices are transient.

Each Family Membership is unique for one Family/User pair and has no role. `users.current_family_id` is a nullable preference that application code validates against live membership. Family creation, membership removal, account deletion, and Family deletion use a shared lock order; final membership removal is blocked unless the Family itself is explicitly deleted.

Store, Store Section, Ingredient, Recipe, and Recipe Tag names use application-generated byte-stable normalized keys with Family-scoped unique constraints. Stores own an optimistic Section-order version. The `store_store_section` association owns contiguous positions and enables the composite Store Placement foreign key. Store Sections also store required `#RRGGBB` colour and nullable allowlisted icon key.

Ingredients store one nullable canonical metric package quantity (grams or millilitres), optional piece count, optional description, optional Store Placement, and nullable archive timestamp. Database checks enforce positive quantities and valid placement. Ordered same-Family Alternative pairs and one optional complete Nutrition Profile are separate constrained records.

Recipes store explicit Family ownership, normalized unique name, positive base servings, optimistic version, approved source/duration/Notes metadata, optional complete nutrition override, and nullable archive timestamp. `recipe_ingredients` permits repeated Ingredients but requires contiguous positions, positive canonical quantities, allowed kinds, and same-Family composite references. `recipe_steps` owns contiguous plain-text instructions. Recipe Tags are Family-owned and many-to-many; deleting one cascades only assignments.

Calendar Entries store Family, same-Family Recipe, concrete date, fixed non-null Meal Label key including `unlabeled`, positive Serving Count, and a unique `(family_id, date, meal_label_key, recipe_id)` combination. Saved Shopping Lists store Family, microsecond generation timestamp, source kind, payload schema version, and one immutable JSON payload; an index over Family, timestamp, and identifier supports bounded newest-first cursor history.

The connected Laravel Boost database remains excluded as evidence. Repository migrations and the SQLite plus disposable MariaDB suites are authoritative.

## Ownership and authorization constraints

`CurrentFamilyScope` requires membership-validated context and constrains every Family-owned query before record identity. Cookbook uses it for Store, Section, Ingredient, Recipe, Tag, and media commands; Meal Planning uses it for Calendar and generation adapters; Shopping Generation uses it only in the snapshot application layer. Client Family identifiers, cookies, route identifiers by themselves, and stale preferences cannot select ownership.

Composite foreign keys preserve same-Family references for placement, Recipe children, Tag assignments, and Calendar Entries. Application validation still resolves each related identifier inside Current Family so failures become intentional not-found or Czech field errors rather than database exceptions. Tests use two Families and equal members for every module boundary.

## Names, archival, deletion, and files

Normalized keys keep SQLite and MariaDB uniqueness semantics aligned and race-safe. Ingredient and Recipe archive is reversible, preserves names, relationships, media, and existing live references, and blocks ordinary editing until restoration. Store, Store Section, Recipe Tag, Calendar Entry, Saved Shopping List, and Family use their approved hard-deletion lifecycles.

Store or association deletion clears the exact Ingredient placement fields required by ADRs 0012 and 0015. Tag deletion removes assignments but leaves Recipes. Family deletion cascades all owned rows. Private media deletion is coordinated with hard Store, Section, and Family deletion: file backups allow the action to restore media and roll back the database transaction when storage cleanup fails. Archive retains files.

## Units and exact quantities

Package quantities, Serving Counts, Recipe Ingredient quantities, nutrition bases, and macro values use `DECIMAL(20,6)`. Inputs with greater normalized scale are rejected. Application adapters normalize metric units into grams or millilitres, while piece remains its own canonical kind. Domain calculation converts finite decimals into exact rational values and quantizes only at presentation/snapshot boundaries.

Removing an Ingredient package kind checks both Nutrition Profile and indexed Recipe Ingredient dependencies. Generator package Purchase Quantity is the ceiling of the globally aggregated exact package fraction; no per-line persistence is introduced for transient output.

## Placement and ordering integrity

Each Store–Section association owns a position unique within its Store. Reorder submits the complete identifier sequence and optimistic version, locks the Store, validates exact membership, and rewrites contiguous positions transactionally. Stale versions are rejected without overwrite. Section deletion repeats the contiguous rewrite for every affected Store and advances their versions.

An Ingredient Store Placement may reference a Store alone or one of that Store's associated Sections. A database check requires Store whenever Section is present, and the composite foreign key guarantees the pair. Detach and deletion actions lock and update affected placement rows atomically before removing the association or owner.

## Recipe integrity

Recipe create/update accepts one complete aggregate. The action validates and locks the aggregate root and same-Family dependencies, then replaces scalar state, ordered Ingredient lines, Steps, Tags, and optional override in one transaction. A stale version, duplicate normalized name, unavailable Ingredient, invalid quantity kind, invalid Tag, or failed child write leaves all prior state intact. [ADR 0032](../adr/0032-save-recipes-as-versioned-aggregates.md) records the boundary.

Recipe Ingredient lines deliberately lack uniqueness on `(recipe_id, ingredient_id)`. Positions are unique within a Recipe, and a focused `(ingredient_id, quantity_kind)` index supports package-kind dependency protection. Recipe Steps remain separate from Recipe Notes.

## Calendar integrity

Persistence maps absent Meal Label to `unlabeled`. Duplicate create and collision-producing edit lock or retry around the unique key, add the submitted Serving Count exactly, and preserve one row. Archived-Recipe entries allow only Serving Count change or deletion. Calendar Days and Simple Plans require no tables.

## Immutable Shopping List history

Saving freezes a successful transient result and source provenance through the explicit `SavedShoppingListV1` serializer. Exact rational quantities, internal kinds, localized labels, grouping, contributions, Alternatives, and display values are copied into the schema-owned payload rather than storing the live Inertia projection by reference. The decoder validates the entire shape and rejects unsupported or corrupt versions intentionally.

Every accepted save creates a distinct row. The history index selects only summary columns and uses cursor pagination; detail alone loads JSON. Model guards reject payload mutation after creation. Live Recipe, Ingredient, Store, Section, Calendar, or localization changes do not recalculate history.
